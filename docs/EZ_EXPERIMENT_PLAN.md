## 0. 一句话结论

**现在最该提的不是训练实验，是两发诊断。** 理由很简单：

> smoke 已经跑通了 **G=2 / turns=16 / 1 步 / TPS=2**，
> 而正式配置是 **G=16 / turns=30 / 25 步 / TPS=8**。
> 这中间 **从没有一个中间态被验证过**，一次要放大所有维度。

而 8 卡排一次队要 15–25 小时 —— 拿主实验去试这个跳跃，代价是**一天只能试一次**。

## 1. 现状盘点：已验 vs 未验

| 维度 | 已验证（smoke） | 正式配置（论文 Table 3） | 放大倍数 |
|---|---|---|---|
| GRPO group size `G` | **2** | **16** | **8×** |
| solve-rate rollouts `G_P` | 2 | 8 | 4× |
| proposer/solver turns | 12–16 | **30** | ~2× |
| 每 outer loop 步数 `M_P/M_S` | **1** | **25** | 25× |
| outer loops `N` | 1 | 4 | 4× |
| `tasks_per_step` (8 卡) | 2 | 8 | 4× |
| **env slot 总数（8 卡）** | **12** | **320** | **26×** |

三个最可能先炸的地方：

1. **显存**：`G=16` 意味着同一时刻挂在图上的轨迹条数是 smoke 的 8 倍。
   GPU_UTILIZATION_PLAN §2 的预算表是按" rollout batch"算的，G=2 时用掉的量远没到上限。
2. **CPU/env**：320 个 textworld slot 打 64（二期）/96（三期）核，**超订 3–5 倍**。
   §4 已经警告过，但从来没实测过真实开销。
3. **proposer 接受率**：smoke 实测 `r0=1/2, r1=0/2`（**全局 25%**）、8 卡那发 **12.5%**，
   而 Phase 2 的验收线是 **≥60%**。

> ⚠️ 第 3 条有个重要缓解因素：smoke 跑的是 `turns=12/16`，而 prompt 明确要求
> "探索 10–20 个动作后才 finish"，正式配置是 `turns=30`。
> **25% 很可能只是 turns 太短的假象。** 但这是推测，得用数据说话 —— 见 E0。

## 2. 实验清单（按性价比排序）

### E0 · proposer 接受率诊断 —— **第一发，今天就提**

**做什么**

1. 补一段日志（约 5 行）：把 `validity_filter` 的**拒绝原因分布**打出来。
   `ez_proposer.py:320` 已经把 `reason` 存进了 `ProposerRollout.reject_reason`，
   但**从来没汇总到日志** —— 所以我们只知道 `accept=1/2`，不知道是哪条规则拒的。
2. 跑两发 dry-run，固定 seed，只改 turns：
   - `EZ_SMOKE_TURNS=16`（复现 smoke 的 25%）
   - `EZ_SMOKE_TURNS=30`（正式配置值）

**为什么最先**

所有后续实验的输入都是 proposer 出的题。25% 接受率意味着 **3/4 的 GPU 时间在生成
注定要被丢掉的垃圾**，而且更糟的是：这 3/4 还会污染任务池多样性。
在不知道是"turns 太短"还是"prompt/格式没对齐（不确定项 U7）"之前，
开训就是把问题埋进几小时的训练里，事后根本分不清是超参问题还是数据问题。

这条不确定项**30 分钟内就能证伪**，是全清单里信息价值/成本比最高的一发。

**判据**

| 结果 | 下一步 |
|---|---|
| turns=30 时 accept ≥ 60% | Phase 2 验收过 → 直接进 E1 |
| turns=30 时 accept 30–60% | 看 reason 分布：若集中在 `unsupported_objects`（启发式抽词误杀）→ 放宽规则 i/iii；若集中在 `redundant_subtask` → 调 Jaccard 阈值 0.6 |
| turns=30 时 accept < 30% | 大概率是 U7（Qwen3-4B **base** 遵循工具格式能力差）→ 需要先做 few-shot 冷启动或小步 SFT 打底 |

**成本**：2 卡 debug，2 发 × ~10 min

```bash

  --export=ALL,NPROC=2,EZ_SMOKE_TPS=2,EZ_SMOKE_TURNS=30 \
  ~/ztwang/selfplay/scripts/ez_smoke_8gpu.sbatch
```

### E1 · 正式 `G=16` 首次试跑 —— **最有价值的一发，零改代码**

**做什么**

`ez_train.py:323-330` 的 dry-run 块允许用环境变量覆盖 `G/G_P/TPS/turns`，
所以这一发**不用改一行代码**：

```bash
sbatch -p debug -t 00:28:00 --gres=gpu:2 --cpus-per-task=16 --mem=240G \
  --export=ALL,NPROC=2,EZ_SMOKE_TPS=2,EZ_SMOKE_TURNS=20,EZ_SMOKE_G=16,EZ_SMOKE_G_P=8 \
  ~/ztwang/selfplay/scripts/ez_smoke_8gpu.sbatch
```

（dry-run 会强制 `M_P=M_S=1`、只跑 1 个 outer loop —— 但第 0 步就是**最费资源**的一步，
用来探显存/时间天花板正好。）

**回答四个问题**

| # | 问题 | 看哪行日志 |
|---|---|---|
| ① | G=16 会不会 OOM / 单步多久 | `[outer 0][P0] ... 196s` 那行的耗时 + OOM 与否 |
| ② | env slot 真实占用 | `[selfcheck] env slots: ... N rank 全局 X` |
| ③ | **Eq.7 子任务奖励有没有区分度**（论文 Prop 1） | `rew_spread` / `诊断 adv_spread=...` 中 >0 的组占比 |
| ④ | 8 卡总时长能否推算 | 单步时间 × 8/2 外推 |

**为什么这一发最重要**

- **`G=2→16` 是从没走过的路**，且是清单里唯一一个"不跑就完全不知道答案"的问题。
- 它顺带重新校准我们对本次算法修改的认识：
  `adv_ddof` 的差异在 G=2 时是 **41%**，到 G=16 只剩 **3.3%**
  （`sqrt(15/16)`）。我们在 G=2 的 smoke 上看到的 `adv_spread=1.414`，
  到 G=16 会是完全不同的图景。**在真实 G 下重新量一次，才知道这次修改到底值多少。**
- Prop 1（可分解奖励把 collapse 率从 ~100% 降到 <50%）是论文的**核心方法贡献**。
  至今只在合成样例上验证过奖励函数，没在真实 rollout 分布上看过。

**判据**：不 OOM；单步时间可外推到预算内；存在 `adv_spread > 0` 的组

**风险与退路**：30 min 大概率不够。备选三条：
① 降 `EZ_SMOKE_TURNS=16`；② 退回 `G=8`（仍能验证"G 不是 2"的关键跨度）；
③ 换 `i64m1tga40u8ka` 分区给 `-t 02:00:00`（排队换时间）。

### E3 · 8 卡正式主实验（4 outer loops）—— **主结果，最后提**

**前提**：E0 过（accept ≥60%）+ E1 过（G=16 可行）

**提之前必须先补一件事：断点粒度**

现在是 `ez_save(..., f"outer{outer+1}", ...)` —— **每个 outer loop 结束才存一次**。
按 E1 实测的单步时间外推，一个 outer loop（25+25 步）可能是 **1–5 小时**。
排队 15–25 小时换来的作业，跑到第 3 小时 OOM 或者 env 崩，**整个 loop 白跑**。

改成每 N 步存一次（`N=5` 左右），仍然遵守"只留最新一个"的铁律
（`ez_save` 里已有 `shutil.rmtree(ckpt_dir)` 删旧逻辑，复用即可）。

**超参决定**：`tasks_per_step=8`（`world` 的倍数，红线 B 要求；
也是 `EZ_DDP_PLAN.md` §5 推荐的 A 方案：固定全局 batch）

**成本**：8 卡，三期 ~15 h 排队 + 8–20 h 训练（论文给的是 ~15 node-hours）
**目标**：复现 ALFWorld 85.07±1.6，判成功线 ±5 分

## 3. 依赖关系

```
E0 (accept 诊断, ~10min×2)
 │  ≥60%?
 ├── 否 ──→ 修 prompt/过滤规则/U7 冷启动 ──→ 重跑 E0
 └── 是 ──→ E1 (G=16 首跑, 30min~2h)
             │  可行?
             ├── 否 ──→ 降 G/TPS/turns，或先做 P0-B KV cache
             └── 是 ──→ E2 (离线量化, 0 成本)
                         │
                         ├─→ E4 (评测开发，可与 E3 并行)
                         └─→ [E3 前提] 改断点粒度为每 N 步
                                  │
                                  └─→ E3 (8 卡 4 outer loops) ──→ E5?
```

**关键原则**：每级只放大 1–2 个维度，且**优先在最便宜的分区（debug 30 min）上放大**。
8 卡一发的排队成本决定了它必须是"已经知道会成功"的那一发，而不是探索性的一发。
